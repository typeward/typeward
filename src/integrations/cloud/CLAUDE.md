# Cloud sync engine — full contract

Moved from the root CLAUDE.md architecture seams; the root keeps a stub.

- **Cloud sync engine** (`src/integrations/cloud/core/engine.ts`) — generic bidirectional orchestration. One `SyncEngine` per active cloud-backed project. Local cache layout: `<projectsRoot>/.remote-cache/<provider>/<projectId>/`; the cache *is* a normal Typeward project (same `.typeward/` sidecar, same watcher, same compile pipeline). Provider state under `<cache>/.typeward/integrations/<providerStateSegment(providerId)>/` (cursor + ID/path map + `sync-state.json`). **That segment must stay escaped (2026-08-28):** a provider id is an identifier, not a filename, and the WebDAV one is `webdav:<username>@<host>`, whose colon is illegal in a Win32 path component, so the raw id failed every cloud project create/open on Windows with os error 123 at the first cursor write. `providerStateSegment` percent-encodes the illegal characters (reversibly, so two account ids can never merge their baselines onto one directory), and `SyncEngine.adoptLegacyStateDir` renames a directory left under the raw id before either loader runs, because macOS and Linux accept that name and dropping its cursor plus manifest would read as a first run: exactly the destructive whole-project re-sync the two loaders refuse to perform. **Pull** drains every delta page in one pass; **push** is queued from the save path — `saveActiveFile`/`saveAllDirtyFiles` call `notifyLocalSave(rootPath, relPaths)` (`cloud/init.ts`), which feeds `engine.queuePush()`; uploads coalesce on a 1.5s debounce and retry on a 15s backoff. Pull and push are serialized through one promise chain (`runExclusive`) so they never interleave on the shared cursor/cache. **Failure semantics (2026-07-13):** an operational pull failure (download/disk/IPC) aborts the page WITHOUT advancing the cursor so the revision is never silently lost — only `normalizeRemoteRelPath` rejections are skipped per-entry; after 3 consecutive failed attempts of the same page it salvages instead of wedging: successful changes apply, failing entries persist as `pendingRetries` in sync-state.json (retried at the head of every pull pass, surfaced as a persistent error phase naming the files until drained), and the cursor advances. Push is per-item isolated: every batch item (upload or deletion) is attempted, only failures requeue, and one aggregate error arms the backoff — no head-of-line blocking behind an unuploadable file. `recordConflicts` merges by relPath (a clean pass can't erase unresolved conflicts; only resolution clears them), and the local-wins conflict branch records sync state (remote rev + local hash) and queues a push so a replayed page neither re-mints `.conflict-*` sidecars nor clobbers the local winner. **Conditional writes (2026-08-05):** `CloudFsProvider.uploadFile` takes an `expectedRev`, and `pushPass` passes `syncState.files[rel]?.rev`; the WebDAV provider forwards it as `If-Match` (and `deleteRemoteFile` sends the known rev too). This is load-bearing, not an optimization — an unconditional PUT is a **lost update**: another device's edit inside the poll window is replaced, and echo suppression then matches our own new rev on the next delta, so the loss is never detected and no `.conflict-*` sidecar is written, contradicting the preserve-the-loser guarantee below. A file with no recorded rev is a plain create; a 412 surfaces as a named skip rather than a blind overwrite. **Echo suppression:** each upload records its returned `rev` keyed by relPath; when the next delta replays our own write, the matching rev makes the engine skip it instead of minting a spurious `.conflict-*` sidecar. **Provider walks must be bounded:** remote listings are attacker-controlled, so the WebDAV `walk` keeps a visited set and a 20k-entry cap — a cycling listing would otherwise spin the pull pass forever, and because everything serializes through one promise chain that also means queued pushes never drain and `stop()` never resolves. The persisted sync state records provider id/rev plus local content hash/size/mtime for each synced file; conflict detection compares remote rev changes against local hash changes instead of relying on filesystem mtime alone, and remote-delete vs local-edit preserves the local file as a `.conflict-*` sibling before removing the canonical path. The snapshot autosave does NOT push (`.typeward/` is rejected in `normalizeRemoteRelPath`). Remote relative paths are normalized before cache IO; absolute paths, parent traversal, Windows drive prefixes, NULs, and `.typeward/` targets (case-insensitive, any depth) are rejected. Conflict resolution writes the loser to `<name>.conflict-<ISO>.<ext>`; `<ConflictResolverDialog>` (reachable by clicking `<SyncStatusBadge>` when conflicts > 0) resolves them. Engine lifecycle in `cloud/init.ts` — when a project with `integrations.cloudOrigin` becomes active, the matching provider instantiates from settings before the engine starts; a remembered account with no credentials on this machine yields a `DisconnectedTarget` (badge says sync is off) instead of a silent unmount. Provider factory `cloudProviderForAccount(ref)` in `cloud/registry.ts`.

- **Remote layout (2026-09-02):** every cloud project Typeward creates lives at `Typeward/<project name>` on the account, one shared folder at the account base (`core/remote-root.ts`: `CLOUD_PROJECTS_FOLDER`, `remoteFolderSegment`, `remoteProjectFolder`). Before this the New-project dialog listed every directory at the account root and made the user pick one, which meant a new project could not be created until they made a folder on the server by hand. `CloudFsProvider.ensureFolder(id)` (WebDAV: the `webdav_mkcol` IPC over `ensure_collection`, idempotent because an existing collection answers 405) plants both levels, and `createCloudBackedProject` calls it **before** `seedFromRemote`, whose PROPFIND would otherwise 404 on a folder nothing has been written into yet. `listRoots()` is rescoped to the contents of `Typeward/` and reads its absence as an empty list, not an error, so it doubles as "projects already on this server" — clicking one fills the name, and a name that matches an existing folder adopts its files (that is the second-machine flow, and the dialog says so rather than hiding it). `remoteFolderSegment` folds `\ / : * ? " < > |` to `-` and strips control characters plus leading/trailing dots and spaces, so one typed name can never become two path components or a folder Windows silently renames. **No migration:** a project bound under the old scheme keeps syncing against whatever `integrations.cloudOrigin.remotePath` it carries.
